Before the first website byte

1. DNS, routes, and ARP

The browser resolves the hostname to an IP address (or uses a cached answer). The client checks its routing table: 198.51.100.20 is outside 192.168.1.0/24, so it uses gateway 192.168.1.1. ARP resolves the gateway’s IPv4 address to its LAN MAC address. It does not resolve the remote web server’s MAC.

Each Ethernet router similarly resolves its own next hop. ARP broadcasts stay within that link; routers do not forward them. A switch learns source MAC addresses and incoming ports; unknown unicast and broadcast frames are flooded within the VLAN, except back to the incoming port.

2. TCP and TLS setup

A TCP SYN, SYN-ACK, ACK exchange establishes the connection. NAT state is normally created as the outbound connection begins. Then TLS negotiates keys and authenticates the server certificate. The journey starts after this setup, with one illustrative encrypted request segment.

This example uses HTTPS over TCP (HTTP/1.1 or HTTP/2). HTTP/3 uses QUIC over UDP and has different transport headers. DNS and handshake traffic are separate exchanges.

3. Switch vs. router vs. NAT vs. firewall

Layer 2 switch: forwards frames by destination MAC and VLAN. It learns the source MAC. It does not decrement IP TTL or replace endpoint MAC addresses on an ordinary same-VLAN Ethernet forwarding path.

Router: removes the incoming link wrapper, uses the destination IP and longest-prefix route match, decrements TTL, updates the IPv4 header checksum, and builds a new link frame addressed to its next hop.

NAT/PAT: translates IP addresses and, when needed, TCP/UDP ports using a mapping table. It adjusts affected IP and transport checksums. Port preservation is possible; this example deliberately shows a changed port.

Firewall: permits or blocks traffic according to policy and often connection state. Translation and filtering are different functions, even when one home gateway performs both. A combined home gateway may also contain a switch and Wi-Fi access point.

4. What the example simplifies

All inter-device links here are untagged Ethernet; real access and backbone networks may use Wi-Fi, PPP, VLANs, MPLS, tunnels, and many more routers. The documentation-only public IP addresses are illustrative. MAC labels identify interfaces, not actual addresses. No fragmentation, retransmission, TCP options, or offload artifacts are simulated. TLS ciphertext and checksum values are not computed.

The request has an illustrative 180-byte TLS payload and response 900-byte payload, each fitting this example’s MTU. With 20-byte IPv4 and TCP headers, their IP lengths are 220 and 940 bytes; Ethernet adds 14 bytes of header and 4 bytes of FCS. Preamble and inter-frame gap are not included. The return path is symmetric here; real routing can be asymmetric.

5. TTL, checksums, and encryption

Routers decrement TTL by at least one. If it expires, forwarding stops and an ICMP Time Exceeded message is normally generated. The IPv4 checksum protects only the IPv4 header. The TCP checksum covers its header and data plus an IP pseudo-header, which is why changing a NAT IP address affects it. Ethernet FCS protects the frame and is generated for transmission; unchanged frame contents produce the same FCS value.

TLS protects application content between its endpoints. An ordinary switch or router does not decrypt the HTTP request. IP addresses, TCP ports, packet sizes, and timing remain visible. Specialized proxies and TLS inspection are outside this example.
